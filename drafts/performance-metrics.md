지난 글에서 LLM 평가가 왜 어려운지 얘기했다

정답이 하나로 정해지지 않으니 assert 한 줄로 통과/실패를 가릴 수 없다

그래도 숫자로 채점은 해야 한다, 그때 쓰는 지표들이 BLEU, ROUGE, Perplexity, BERTScore다

## BLEU — 번역 품질, 단어가 얼마나 겹치나

번역 품질을 재려고 만들어진 지표다

정답 텍스트와 LLM 출력을 비교해서 같은 단어가 얼마나 포함됐는지 센다

```
정답:  "고양이가 방에 있다"
출력:  "방에 고양이가 있다"
✅ 같은 단어들이 있으니 점수 높음
```

문제는 단어 순서나 의미를 신경 안 쓴다는 것

```
정답:  "고양이가 방에 있다"
출력:  "고양이가 방에 없다"
❌ 단어가 거의 겹치니 점수는 여전히 높게 나옴, 근데 뜻은 정반대
```

"없다"랑 "있다"를 구분 못 하는 지표로 번역 품질을 재는 셈이다

## ROUGE — 요약 품질, 정답을 얼마나 커버했나

요약 품질을 재려고 만든 지표, BLEU랑 계산 방식은 비슷한데 방향이 다르다

BLEU는 출력이 정답 단어를 얼마나 썼는지(precision) 보고, ROUGE는 정답이 출력에 얼마나 포함됐는지(recall) 본다

```
정답:  "기후 변화로 북극 빙하가 녹고 있다"
출력:  "북극 빙하가 녹는다"
✅ 정답의 핵심 단어를 커버했으니 점수 나옴
```

BLEU랑 같은 한계를 그대로 물려받는다, 단어만 보고 의미는 안 본다

## Perplexity — 정답 없이 모델 자체를 재는 지표

BLEU, ROUGE는 정답 텍스트가 있어야 계산되는데 Perplexity는 정답이 필요 없다

모델이 다음 단어를 얼마나 "당연하게" 예측하는지를 재는 지표라서다

낮을수록 좋다, 모델이 다음 단어를 자신 있게 예측한다는 뜻이고 그만큼 자연스러운 텍스트가 나온다는 뜻이니까

반대로 높으면 모델이 다음 단어를 못 예측한다는 뜻, 어색한 텍스트가 나온다

정답 텍스트 없이 모델 자체 품질을 확인하고 싶을 때 쓰는 지표다

## BERTScore — 단어 대신 의미로 비교

BLEU, ROUGE의 근본적인 한계는 단어 일치만 본다는 것

BERTScore는 여기서 한발 나간다, BERT 임베딩으로 단어를 벡터로 바꾸고 "비슷한 의미면 같은 것"으로 판단한다

```
정답:  "차가 빠르게 달린다"
출력:  "자동차가 속도를 내며 이동한다"
✅ BERTScore는 높게 나옴 (의미가 비슷하니까)
❌ BLEU는 낮게 나옴 (겹치는 단어가 거의 없으니까)
```

같은 문장 쌍을 두고 지표에 따라 평가가 완전히 갈리는 지점이다, 어떤 지표를 쓰느냐가 결과를 결정한다

## 언제 뭘 쓰나

| 지표 | 쓰는 상황 | 한계 |
|------|---------|------|
| BLEU | 번역, 단어 정확도가 중요할 때 | 의미를 무시함 |
| ROUGE | 요약 품질 측정 | 의미를 무시함 |
| Perplexity | 정답 없이 모델 자체 평가 | 실제 품질과 괴리 가능 |
| BERTScore | 의미 유사성이 중요할 때 | 계산 비용이 높음 |

## 공통 한계

이 네 지표 전부 "형식적으로 맞는지"는 잴 수 있어도 "실제로 유용한지"는 못 잰다

BLEU 점수가 높아도 사용자 입장에서 별로인 답일 수 있고, Perplexity가 낮아도 사실이 틀린 문장일 수 있다

그래서 지난 글에서 다룬 Human Evaluation이나 LLM-as-a-Judge를 같이 쓰는 경우가 많다, 숫자 지표로 1차 필터링을 하고 애매한 케이스만 사람이나 다른 LLM이 다시 본다
